# MedTrace MVP

Веб-приложение для учёта партий медицинских изделий внутри одного предприятия. Цикл: приёмка → входной контроль → решение качества → заказ и резерв → фактический расход и выпуск → выходной контроль → разрешение выпуска → отгрузка → прослеживаемость, блокировка и отзыв. Данные и действия хранятся на сервере. Демонстрационные данные вымышленные.

Исходное задание находится в [`docs/ТЗ-MedTrace.txt`](docs/ТЗ-MedTrace.txt), краткое состояние проекта — в [`PROJECT_CONTEXT.md`](PROJECT_CONTEXT.md).
Краткая инструкция для запуска на ноутбуке перед защитой — [`docs/ЗАПУСК-НА-НОУТБУКЕ.md`](docs/ЗАПУСК-НА-НОУТБУКЕ.md).

## Быстрый запуск локальной демонстрации

Требуется Node.js 20+ и npm. Проверено на Node.js 26.11.1.

```bash
npm ci
cp .env.example .env.local
# Замените SESSION_SECRET в .env.local на случайное значение:
# openssl rand -hex 32
npm run db:seed
npm run dev
```

Откройте `http://localhost:3000`. Локальная база PGlite создаётся в `data/medtrace` при первом запуске и сохраняется между перезапусками. `npm run db:migrate` применяет схему отдельно; `db:seed` делает это автоматически и заполняет **только пустую** базу. Повторное заполнение существующей базы не выполняется.

На другом компьютере исходный код запускается теми же командами после установки Node.js и npm. При использовании PGlite это будет **отдельная** база: в ZIP нет данных из `data/` и файлов из `private-uploads/`. Если несколько установок должны видеть общие партии, подключите их к одной PostgreSQL-базе и одному приватному хранилищу. Телефону или планшету исходный код не нужен: они открывают адрес сервера в браузере. Для доступа к серверу по сети нужны явная настройка сетевого адреса и HTTPS; обычные `dev` и `start` слушают только `127.0.0.1`. Не публикуйте демонстрационные учётные записи в сети.

### Вход администратора в локальную демоверсию

После `npm run db:seed` откройте `http://localhost:3000` и войдите:

| Роль | Логин | Пароль |
| --- | --- | --- |
| Администратор демоверсии | `admin@medtrace.demo` | `MedTrace2026!` |

Остальные демопользователи имеют тот же пароль и адреса `warehouse@medtrace.demo`, `qc@medtrace.demo`, `qa@medtrace.demo`, `manager@medtrace.demo`, `operator@medtrace.demo`, `shipping@medtrace.demo`, `auditor@medtrace.demo`. Эти учётные записи предназначены только для локальной демонстрации; в `NODE_ENV=production` вход в организацию `demo-org` запрещён. Для осознанного показа production-сборки с демо-данными можно временно задать `MEDTRACE_ALLOW_DEMO_LOGIN=1` в изолированной среде. Роль администратора не утверждает качество.

Пароль администратора реальной организации задаётся отдельно при `npm run db:bootstrap:remote` и не должен храниться в публичном README.

Для чистого повторного заполнения **только локальной демонстрационной базы** остановите сервер и выполните:

```bash
CONFIRM_DEMO_RESET=yes npm run db:reset-demo
npm run db:seed
```

Команда сброса отказывается работать с `DATABASE_URL` или `NODE_ENV=production`.

## Проверка

```bash
npm run lint
npm test
npm run build
```

Тесты используют отдельную временную PGlite базу, заполняют её демонстрационными данными и проверяют критические переходы, прослеживаемость, разделение партии, права, идемпотентность и конкурентную отгрузку. Для проверки зависимостей запускайте `npm audit --omit=dev`. Для визуального прогона доступен `scripts/browser-qa.ts` с Playwright и установленным Chromium; снимки демонстрации находятся в `qa/`.

## Состав

- Next.js 16, React 19, TypeScript; серверные API в `src/app/api/`.
- PostgreSQL или локальная PGlite; схема и ограничения в `migrations/001_initial.sql`, `002_security.sql`, а для PostgreSQL закрытие Data API в `003_supabase_api_lockdown.sql`.
- Роли: администратор, склад, специалист качества, ответственный за качество, начальник производства, оператор, отгрузка, аудитор. Один пользователь может иметь несколько ролей; проверяющий не утверждает собственный протокол.
- Журнал движений вместо редактируемого поля остатка, резервы, блокировки, идемпотентные ключи и транзакции. В PostgreSQL складские операции сериализуются транзакционной advisory lock.
- Версии спецификаций и документов, аудит и история статусов; утверждённые спецификации защищены триггером от изменения.
- Фактические связи сырья и готовой партии идут через производственный запуск. Разделение входящей партии создаёт две дочерние партии в карантине, документ и отдельные решения качества; родительский остаток становится нулевым.
- Внутренние QR-метки открывают карточку после входа. Отчёты выгружаются в CSV; PDF получается через печать страницы браузером.
- Вложения: PDF, PNG, JPEG, WebP, TXT до 10 МБ, проверка сигнатуры и ограничения размера тела запроса, права на связанную запись, приватное локальное хранилище или необязательный Supabase Storage, ссылки на 5 минут с подписью для конкретного пользователя.
- Сервер проверяет роли и назначение заказа, содержимое повторного идемпотентного запроса, происхождение изменяющих HTTP-запросов, частоту попыток входа и соответствие фактического расхода спецификации. Доступный остаток считается только по пригодным складам; нельзя обойти карантин, вывести зарезервированное сырьё в блокировку, снять защитную блокировку при открытом отзыве или списать активный резерв.

## Настройка PostgreSQL и Supabase

Для подключения нового проекта Supabase:

1. Создайте проект в [Supabase Dashboard](https://supabase.com/dashboard). Для разработки достаточно Free; перед пилотом с реальными данными проверьте тариф, место хранения данных и требования предприятия к резервным копиям.
2. В окне **Connect** проекта скопируйте строку PostgreSQL. Для этого постоянного сервера используйте прямое соединение, если доступен IPv6; для сети только с IPv4 выберите **Session pooler** (порт 5432). В строке замените пароль БД, при необходимости закодировав специальные символы URL; требуйте TLS (`sslmode=require`).
3. В **Settings → API Keys** возьмите project URL, publishable key и secret key. Добавьте в `.env.local` значения `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, `SUPABASE_STORAGE_BUCKET=medtrace-private`. Ключи остаются только на сервере. Старые `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY` тоже поддерживаются, но для нового проекта используйте новые ключи. Файл `.env.local` не включайте в архив и Git.
   На подготовленном локальном компьютере MedTrace URL и ключи уже лежат в закрытом `.env.supabase.pending.json`; команда `npm run db:configure` спросит пароль PostgreSQL в терминале без отображения и соберёт `.env.local`. Этот временный файл не включён в ZIP.
4. Выполните `npm run db:migrate:remote`. Миграция закрывает таблицы MedTrace от прямого доступа через Supabase Data API: включает RLS без разрешающих политик и отзывает права API-ролей. Остальные операции идут через сервер MedTrace и прямое соединение PostgreSQL.
5. Для пустой базы один раз создайте организацию и администратора через `npm run db:bootstrap:remote`. Перед командой задайте `MEDTRACE_ORG_NAME` и `MEDTRACE_ADMIN_EMAIL`. Команда спросит новый пароль администратора в терминале без отображения (от 12 символов); для автоматизации его можно передать временной переменной `MEDTRACE_ADMIN_PASSWORD`, но не хранить в `.env.local`. Команда создаёт приватный bucket и аккаунт Supabase Auth, связанный с профилем MedTrace; она отказывается работать с уже заполненной базой.
6. Выполните `npm run integrations:check`, перезапустите приложение и проверьте вход нового администратора, создание записи и загрузку/скачивание документа. Проверка интеграций отдельно подтверждает PostgreSQL, закрытые таблицы, Auth и приватный Storage bucket.

**Не запускайте `db:seed` в рабочей базе.** Команда запрещает удалённое демо-заполнение без отдельного явного подтверждения; демо-учётные записи не предназначены для эксплуатации. Дальнейшие изменения схемы потребуют отдельных версионированных миграций перед эксплуатацией.

Без `DATABASE_URL` используется локальная PGlite, подходящая для однопроцессной демонстрации. Для рабочего многопользовательского развёртывания используйте PostgreSQL, резервное копирование, HTTPS, управление секретами и внешний приватный файловый сервис. Работа на нескольких экземплярах приложения с локальными `data/` или `private-uploads/` не поддерживается.

Для режима Supabase Auth нужны вместе URL, publishable key и secret key. При полном отсутствии этих значений используется локальная авторизация с bcrypt и серверной таблицей сессий; частичная конфигурация вызывает ошибку. Для Storage дополнительно нужен приватный bucket. Проект Supabase **MedTrace Pilot** создан, но пароль базы ещё не введён в локальную настройку; реальное соединение, вход и операции с облачными файлами пока не проверены.

`SESSION_SECRET` обязателен в рабочем окружении для подписанных ссылок на локальные вложения. В разработке при отсутствии значения создаётся случайный ключ на время процесса. Не храните секреты в Git или ZIP. На внешнем контуре настройте HTTPS, доверенный reverse proxy, лимиты тела запроса и частоты запросов, мониторинг, управление секретами и проверенное восстановление резервной копии. Серверное ограничение входа действует на одну почту: 5 неверных попыток за 15 минут.

## Резервное копирование и восстановление

### Локальная PGlite

Остановите приложение и скопируйте вместе `data/medtrace/` и `private-uploads/`. Для восстановления установите ту же версию исходного кода, остановите сервер, верните обе директории на прежние места и запустите приложение. Проверяйте восстановление на отдельной копии; открытая база не должна копироваться обычным `cp`.

### PostgreSQL

Пример резервной копии и восстановления (запускается владельцем БД в доверенном окружении):

```bash
pg_dump --format=custom --no-owner --file=medtrace.dump "$DATABASE_URL"
createdb medtrace_restore
pg_restore --no-owner --dbname=medtrace_restore medtrace.dump
```

Также сохраните содержимое приватного файлового хранилища или настройте отдельные резервные копии Supabase Storage. После восстановления проверьте вход, карточку партии, документ и след отгрузки. Регулярность и хранение копий определяет предприятие.

## Границы поставки

Это функциональный MVP для пилота, а не валидированная производственная система и не подтверждение соответствия медицинским стандартам. Критерии контроля и нормы из демо должны быть заменены утверждёнными правилами предприятия. Не реализованы индивидуальные серийные номера, ERP/оборудование/внешняя маркировка, автоматическая отправка уведомлений, электронная подпись и серверное формирование PDF. Интерфейс преимущественно русский; казахский словарь покрывает основную навигацию и статусы, но не все формы. Настройка планов контроля и производственных шаблонов пока выполняется через БД, без редактора в интерфейсе. Экран загрузки файла требует указать тип и ID связанной записи вручную. Политики доступа к операциям реализованы на сервере приложения; прямой доступ к таблицам через Supabase Data API запрещён, а отдельные пользовательские RLS-политики не настроены. Перед использованием с реальными данными нужны независимая проверка безопасности, резервного восстановления и валидация процессов предприятия.
